# From observations to an actionable final report

A machine observation is not automatically a website defect. A useful repair workflow must nevertheless say what the user can do next, why, who should do it, and what evidence would demonstrate completion. Version 0.5 separates those decisions explicitly.

## Four decision buckets

1. **Confirmed fix:** evidence and a documented review establish a mismatch with the intended behavior. Include affected URL/entity, source/date, intended versus actual behavior, concrete proposed steps, dependencies, proposed role, sequencing reason and verifiable acceptance. Confirmation describes the supplied review, not independent truth certification or permission to deploy.
2. **Needs verification:** an observed signal or important evidence gap requires a specific check before changes. State the exact check, evidence needed, decision condition and next action if confirmed. Missing data is not a defect.
3. **Optional improvement:** a reasoned usability/content/marketing opportunity, explicitly distinct from a fault or demonstrated ranking benefit. State the hypothesis and how to evaluate it; no invented traffic/ROI.
4. **Keep / not applicable:** preserve an intentional configuration, record no supported change in the inspected scope, or explain a sourced business N/A. Zero triggered rules cannot establish whole-site health.

Every action must have executable steps, a proposed role (not an invented person), dependencies, and acceptance criteria. Ordering needs a reason grounded in severity, business purpose and evidence. Unknown business impact cannot become a high-priority claim. Investigation sequencing may still say “verify before changing this directive” without pretending revenue urgency.

## Actual AI and CLI responsibilities

- The collector supplies a bounded public snapshot; it does not diagnose business intent.
- The report script applies supported rules and builds concrete action/investigation records. Its default review status must remain honest.
- The agent reads actual evidence, reuses authorized context, asks missing essentials, and records explicit review decisions. A schema-valid decision remains a supplied assertion, with reviewer/date/provenance visible.
- The final report is generated by the script from evidence and any validated supplied review. An analyst's testing commentary is a separate file; it must not be presented as the raw skill output.
- CLI is noninteractive; no hidden LLM call, memory connector, login or website modification occurs.

## Truthfulness tests

A useful test suite includes real evidence with no supported faults and clearly labeled synthetic defects. Test recall only for supported rules, intentional exclusions, absent measurements, contradictory review, unrelated evidence IDs and action specificity. Do not count six headings or total tests as proof of six-dimensional SEO coverage.

Backlinks illustrate the boundary: without a reliable export, the correct result is a concrete evidence request/inspection task, not a fabricated authority problem. Canonical/noindex disagreement requires intent review; product/local field disagreement requires an authoritative value, not automatic replacement of one side. Empty metadata is a visible signal but not a proven ranking penalty.

最终交付必须回答“做什么、为什么、谁来做、做完如何验证”。分为已确认修复、待验证、可选优化、保持不动/不适用四组。证据不够就给具体调查步骤，不能强造网站缺陷；确认结论要显示是谁、何时、依据什么做出的判断。

真实网站只是测试样本。没有发现规则覆盖的问题可以是正确输出，但必须明确覆盖范围与下一步检查，不能靠含糊占位文字冒充完整修复报告。程序原始输出与分析者的测试说明分别保存；人工或 AI 复核也不得冒称独立验证、实际部署或 SEO 成绩。

## Explicit review input and execution

`--review REVIEW.json` is optional. Run the initial report first to obtain real issue/evidence IDs. A review file is a supplied decision record, not a hidden AI execution. Top-level fields: nonempty `reviewer`, nonempty `source`, ISO `date`; optional `decisions` and `section_reviews` arrays. Review dates must be compatible with the observation/report dates. See the actual [synthetic reviewed case](../cases/actionable-handoff/) for runnable files.

Each finding decision requires `issue_id`, `evidence_ids` belonging to that finding, `decision` (one of the four bucket names), `rationale`, `intended_behavior`, and `business_context_basis`. `steps` and `acceptance`, when supplied, must be nonempty lists of nonempty strings; both are required for `confirmed_fix`.

Additional gates: paired field mismatches need `authoritative_source`; HTTP-error fixes require `url_lifecycle: active`; noindex/canonical decisions need explicit `visibility_intent` and conflicting exclusion/alternate intent stays verification. An aggregate CWV threshold exceedance alone cannot confirm a repair cause. Applicability must be established before a specialist fix. These checks validate consistency, not authenticity of the reviewer's claims.

Section reviews use `dimension` instead of an issue ID, real relevant `evidence_ids`, the same rationale/intended behavior/business basis, and only `keep_or_not_applicable` or `needs_verification`. They do not erase existing findings or clear unresolved evidence gaps. No synthetic issue needs to be invented to record a scoped keep decision.

Run from repository root, preserving outputs:

```sh
python scripts/six_dimension_report.py SNAPSHOT.json --context CONTEXT.json --out /tmp/seo-initial-new
# Read actual evidence and write review decisions referencing that run's IDs.
python scripts/six_dimension_report.py SNAPSHOT.json --context CONTEXT.json --review REVIEW.json --out /tmp/seo-final-new
```

Add `--supplement SUPPLEMENT.json` to both runs when the same optional measurements are part of the evidence. The final `report.md`/`report.json` are direct program outputs. Store an analyst's validation commentary separately. Four buckets can legitimately be empty; supported evidence determines the decision, not a quota.

For reproducible review, copy `input_fingerprint` from the initial report into the review JSON. The program checks it against the exact snapshot/context/supplement combination. Without it, review provenance explicitly warns that evidence IDs are locator-based and cannot rule out changed source values. A dated review cannot precede the evidence it cites. A reviewed action's qualitative state (`reviewed_fix_sequence`, `verify_before_change`, `optional`, `retain`) describes its workflow position, not a ranking benefit or invented business urgency.
